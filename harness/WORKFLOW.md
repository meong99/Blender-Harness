# 공통 제작 절차 v1.2.0

## 기존 프로젝트 설치와 업데이트

설치는 [INSTALL.md](INSTALL.md)를 따른다. 기존 프로젝트 루트에 ZIP 내용을 덮어쓰지 않는다. `install --project <경로>`는 `.blender-harness/`에 하네스를 격리하고, 루트 AGENTS.md의 기존 바이트를 보존하면서 관리 구역만 추가한다. 설치된 문서의 상대 경로는 `.blender-harness/` 기준이다. 기존 프로젝트 규칙과 사용자 지시를 우선하고 Blender 제작 요청에만 하네스를 적용한다.

`install --project <경로> --repo meong99/Blender-Harness`는 GitHub의 최신 정식 Release를 설치하고 업데이트 저장소를 기록한다. 설치 후 `check-update`는 버전만 확인하고, `update --dry-run`은 다운로드 검증 및 변경 계획만 출력하며, `update`가 실제 적용한다. 로컬 ZIP은 `update --package <ZIP>`으로 적용한다. 실행 중인 제작이 있으면 완료 또는 실패 상태가 된 뒤 업데이트한다.

업데이트는 관리 파일별 기존 배포 해시와 현재 파일 및 새 배포를 비교한다. 프로젝트의 비관리 파일과 `runs/`는 보존한다. 로컬만 바뀐 파일은 유지하고 양쪽이 다르게 바뀐 동일 파일이나 관리 구역 충돌은 전체 적용 전 중단한다. 코드 문장의 자동 의미 병합은 하지 않는다. 변경 파일은 `.backups/`에 저장하고 정상적인 쓰기 오류 시 이전 바이트로 복원한다. 전원 중단의 자동 복구까지 보장하지 않는다. 작업별 요구를 전역 규칙으로 바꾸지 않는다.

v1.1부터 에이전트가 `templates/quality-plan.json`을 참고하여 품질 계획을 작성하고 new에 `--quality-plan <계획.json>`을 전달한다. review에는 `--surface-notes <접합부 검수>`와 `--reference-notes <시안 비교 또는 해당 없음 사유>`를 함께 전달한다. 아래 기본 명령 예시에도 이 인수를 추가한다. 사용자가 JSON이나 긴 프롬프트를 작성할 필요는 없다.

## 표면 연결과 시안 비교

- `intent`: 연결될 부분, 분리할 부분, 의도한 틈의 판단과 가정을 기록한다. 사용자가 분리·가동을 명시하면 우선한다. 합치면 중요한 기능이 달라지는데 시안이 모호할 때만 질문한다.
- `continuous`: name, objects(정확한 메시 이름), closed(닫힌 표면 요구 여부). 평가된 메시에서 연결 성분 합이 1이어야 한다. closed=true일 때 non-manifold edge도 0이어야 한다. 모든 모델의 구멍을 막으라는 규칙이 아니다.
- `separate`: 서로 다른 오브젝트로 남아야 할 이름들을 한 그룹에 기록한다. 예: Vase와 Badge, Box와 Lid. fuse_voxel 도우미는 같은 separate 그룹의 두 부품을 합치는 호출을 사전에 거부한다. 직접 bpy 코드로 합쳐 부품이 사라지는 경우에도 사후 검사에서 실패한다. 이름만 남긴 가짜 부품이나 실제 가동 간격을 검증하는 보안/물리 검사기는 아니다.
- `views`: 최대 3개 고정 카메라. location/target/type과 ORTHO의 ortho_scale 또는 PERSP의 lens를 지정한다. role=joint는 접합부 확대, role=reference는 시안 비교다. continuous가 있으면 joint가 필요하고, 입력 이미지가 있으면 reference가 필요하다.
- reference에는 reference_index(입력 순서, 0부터), 촬영 조건/측정 근거 provenance, landmarks를 지정한다. landmark는 name/object/anchor/uv/tolerance_px를 갖는다. anchor는 평가된 월드 바운딩 박스 안의 0..1 위치, uv는 시안 좌상단 원점 0..1이다. 현재 기능은 부품 크기·위치 비교이며 임의의 표면 특징점이나 전체 실루엣 자동 매칭은 아니다.
- 시안과 같은 프레임·비율의 카메라를 맞추고 비교한다. 사진 촬영 조건을 모르면 추정이라고 기록하고 허용 오차에 반영한다. 조명 차이를 픽셀 색상 차이로 품질 판정하지 않는다. 기본 추가 프리뷰는 640×640, 16샘플이다.
- 계획은 실행 생성 시 복사·해시 고정한다. 결과에 맞춰 기준점을 옮기지 않는다. 기준을 바꾸면 새 실행으로 구분한다.
- HTML에 시안·렌더와 목표/측정 기준점을 표시하고 JSON에 오차를 남긴다. 실제 이미지 검수 후 surface-notes/reference-notes를 기록한다. 수치 실패는 pass 불가, 수정 기준으로 쓸 때 partial과 결함을 기록한다.
- 연결 성분 1은 매끄러운 접선·곡률, 내부 교차 없음, 시안 재현을 보장하지 않는다. 클레이 확대에서 경계·찌그러짐·음영을 확인한다. 기존 비대상 보호 검사도 유지한다.

`modeling.fuse_voxel`은 에이전트가 명시적으로 선택해 호출하는 초기 형상 통합 도우미이며 자동 실행되지 않는다. 허용한 대상만 합치고 기존 대상 이름을 출력 이름으로 유지한다. modifier를 평가한 뒤 토폴로지를 다시 만들므로 UV·세부 속성 보존은 보장하지 않는다. SMOOTH 반복은 해당 대상 전체에 적용되므로 실루엣 변화도 검수한다. 하드서피스·얇은 부위·완성된 디테일에 무조건 적용하지 않는다.

몸체 단계에서 결함을 고친 edit 검수본에서도 detail을 계속할 수 있다. 최종 단계에서는 검수한 기준 파일을 그대로 불러와 시안/접합부 프리뷰를 재사용하고 수치는 재검사한다. 최종 컬러·클레이 4장만 새로 렌더한다. 기준 파일·증거 해시가 바뀌면 재사용하지 않는다. v1.0 실행은 기존 기준으로 계속 읽을 수 있다.

## 요청 처리

사용자가 대상과 참고 이미지만 주어도 진행한다. 이미지에서 실루엣, 비율, 특징 부품, 재질을 추출해 제작 우선순위를 짧게 기록한다. 알려진 물체는 합리적인 실제 크기를 가정하고 알린다. 중요하고 추정 불가능한 조건만 질문한다. 사용자가 추가 조건을 주면 기본값보다 우선한다.

기본값의 단일 출처는 `harness/defaults.json`이다. 사용자 요청은 실행별 manifest의 request와 설정에 남긴다. 설정 변경은 새 실행을 만들기 전에 적용하고, 실행 중인 설정 스냅샷은 유지한다.

이 하네스는 **에이전트가 작성한 Blender 코드의 공통 실행·검수·기록 계층**이다. CLI 자체가 자연어로 형상을 생성하지 않는다. 백엔드는 포함된 blenderwright 공식 dispatcher/handlers이며 통신 방식은 격리 CLI다. 실시간 MCP라고 설명하지 않는다. Blender 내부 실행 코드는 신뢰하는 에이전트 작성 코드이며 보안 샌드박스가 아니다.

## 한 번만 준비

1. `harness.ps1 doctor`로 Blender와 포함된 addon을 확인한다.
2. `new --name <이름> --request <요청과 가정> --reference <이미지>`로 실행 폴더를 만든다. reference는 반복 가능하다. 크기는 `--dimensions <폭> <깊이> <높이>`로 미터 단위를 지정한다.
3. 현재 대화의 정확한 세션 로그가 있으면 `--session-log <경로>` 또는 HARNESS_SESSION_LOG를 제공한다. 다른 대화의 로그를 임의로 선택하지 않는다. 없으면 토큰 미계측을 허용한다.
4. 모델별 형상 코드만 작성한다. 실행기, 스튜디오, 저장 검사기, 보고기를 다시 작성하지 않는다.

아래 명령은 Windows에서는 `.\harness.ps1` 뒤에, 다른 환경에서는 `python3 harness/cli.py` 뒤에 붙인다. `new`가 출력한 실행 ID를 이후 `--run`에 사용한다.

## 제작과 검수

```text
stage --run ID --phase body --source builder.py
review --run ID --revision 001_body --decision pass --notes "실루엣·비율·접지 검수 결과"
stage --run ID --phase detail --source builder.py --base 001_body
review --run ID --revision 002_detail --decision pass --notes "형상·재질·특징 검수 결과"
```

- 몸체는 512×568, 16샘플 클레이 앞·옆·뒤 3장이다. **실제 이미지를 연 후** 비율·실루엣·접지·찌그러짐을 검수한다. 기록만 작성해 통과시키지 않는다.
- 검수 전이나 검수 후 파일·이미지 해시가 바뀌면 다음 단계는 실행되지 않는다.
- 디테일은 검수한 몸체 .blend에서 계속한다. 기본 컬러 사선 1장, 필요할 때 `--views hero back` 등 관련 시점만 최대 3장까지 지정한다.
- 수정이 필요하면 `review --decision revise`로 결함을 기록한다. 이 상태의 체크포인트는 다음 작업의 기준이 될 수 없으므로 보존 가능한 마지막 검수본을 사용한다. 결함을 인정하고 일부를 보존해 수정하려면 `partial`과 구체적인 결함을 기록하고 해당 체크포인트를 기준으로 삼는다.
- 국소 수정은 `stage --phase edit --base <검수본> --targets <정확한 오브젝트 이름들> --source builder.py`로 수행한다. 비대상 오브젝트의 평가 형상·변환·UV·주요 재질 설정 변경을 검사한다. 모든 Blender 데이터에 대한 완전한 의미적 동등성 검사는 아니다. 공용 재질 변경은 다른 오브젝트에도 영향을 줄 수 있다.
- 시각 수정은 2회를 우선 목표로 삼는다. 추가 수정은 눈에 보이는 결함과 이유를 기록한다. 15분 초과 자체를 실패나 품질 통과로 처리하지 않는다.

## 최종 결과

```text
finalize --run ID --base <검수한 detail 또는 edit ID>
review --run ID --revision <출력된 final ID> --decision pass --notes "최종 컬러·클레이 4장 실제 검수 결과"
status --run ID
```

최종은 1080×1200, 64샘플 컬러 앞 사선·뒤와 클레이 앞 사선·뒤 4장이다. 저장본을 독립 프로세스에서 한 번 재열어 형상, 소스·참조 패킹을 확인한다. 같은 기준 파일의 finalize 재호출은 기존 결과를 반환한다. 검수 후 completed가 되며, 한계가 남으면 partial을 기록한다. 실패 실행은 검수 통과로 바꿀 수 없다. 완료 실행은 보존하고 추가 작업은 새 실행에서 한다.

자동 메시 진단은 참고 지표다. 극소 면·모서리 수를 0으로 만들기 위해 전역 재메싱하거나 반복 정리하지 않는다. 눈에 보이는 결함, 의도하지 않은 관통·틈·울퉁불퉁함은 고친다. 프리뷰 검수와 저장 확인을 생략하는 방식으로 시간을 줄이지 않는다.

## 모델 코드 계약

`templates/example_asset.py`와 `harness/modeling.py`를 참고한다.

- `build_body(ctx)`, `add_details(ctx)`, `edit(ctx)` 중 해당 단계 함수를 제공한다.
- ctx에는 asset(ASSET 컬렉션)과 dimensions(미터 폭·깊이·높이 또는 None)가 들어온다.
- 모델 오브젝트는 ASSET에 넣는다. 앞은 -Y, 바닥 z=0, 중심 x=y=0을 기준으로 제작한다. STUDIO와 H_ 이름은 실행기가 소유한다.
- detail은 검수한 몸체를 보존하면서 부품을 추가한다. 필요하면 명시적인 edit에서 기존 부위를 고친다.
- 열린 사용자 장면은 건드리지 않는다. 모든 실행은 별도 factory-startup Blender 프로세스에서 수행한다.
- 같은 실행에 동시 쓰기를 하지 않는다. 여러 자산은 실행 폴더와 프로세스를 분리한다.

## 기록과 이식

manifest.json, report.md, runs/CURRENT.md는 명령 실행 시 자동 갱신된다. .blend에 모델 소스와 참고 이미지를 패킹하고, 원본 코드·명령별 시간·실패 로그·검수·해시를 실행 폴더에 보존한다. 과거 결과를 덮어쓰지 않는다.

시간은 실행 생성~최종 검수의 벽시계 시간(에이전트 작성·대기 포함), 단계별 프로세스 시간, blenderwright 명령별 시간을 구분한다. 완료 뒤 status를 조회해도 완료 시간은 늘어나지 않는다. 최종 재열기 시간은 manifest의 verification_seconds에 별도로 기록한다.

토큰은 실행 전후 공유 세션 누적값의 차이다. 로그가 아직 flush되지 않은 마지막 호출과 실행 생성 전 요청 해석은 빠질 수 있고 다른 작업이 섞일 수 있다. 캐시·추론 토큰은 부분집합이므로 총 토큰에 다시 더하지 않는다. 실제 결제액이나 자산 전용 토큰으로 단정하지 않는다.

새 제작마다 프로젝트 설계 문서를 다시 쓰지 않는다. 규칙 변경 때만 AGENTS/defaults/WORKFLOW와 관련 문서를 함께 갱신한다. 역사적 비교 보고서는 원래 기준을 유지한다.

`bundle --out dist/blenderwright-harness-v1.2.0.zip`은 규칙·설정·코드·예제·blenderwright addon 및 라이선스만 묶는다. 참조·사용자 결과·세션 로그·Blender 실행 파일·다른 후보 설치는 제외한다. ZIP 내부 PACKAGE.json과 옆 manifest에 포함 파일과 해시가 저장된다. GitHub 태그와 defaults.json의 버전이 같을 때 Release workflow가 테스트 후 이 ZIP을 배포한다.
